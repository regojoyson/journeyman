# Dependency Upgrade Campaign Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring every third-party dependency in the monorepo to current stable (majors included), with the minimum code changes each major requires.

**Architecture:** Six sequential clusters on one branch (`chore/deps-latest-stable`, already created off `master`), one commit per cluster, one PR at the end. After every cluster the gate `npm run check && npm test && npm run build:web` must pass before the next begins.

**Tech Stack:** npm workspaces, TypeScript 6, Vitest, Vite, React, Fastify, Tailwind, zod, Octokit.

---

## Design notes (read before starting)

- **This is not test-first work.** Each task is `bump → install → run the gate → fix what the gate flags → re-run the gate → commit`. The existing 125-file Vitest suite plus `npm run check` and `npm run build:web` are the tests. Do **not** write new tests for version bumps.
- **The gate is three commands**, run from the repo root, in this order:
  ```bash
  npm run check        # typecheck (all workspaces) + import-boundary check
  npm test             # vitest run across the 9 test packages
  npm run build:web    # production bundle
  ```
  All three must exit 0. If any is red, fix it inside the same task before committing — never commit a red gate.
- **Branch is already created** (`chore/deps-latest-stable`) and the spec is committed on it. Confirm with `git branch --show-current` → `chore/deps-latest-stable` before starting.
- **Many bumps need zero code changes** — the call sites already match the new API (verified during planning). Where that's the case the task says so; you still run the full gate to confirm.
- **Per-major breaking-change checklists** are included inline. They are the actual things to look for when the gate goes red — not placeholders. If the gate is green, you skip them.
- **One commit per cluster.** Commit message format is given in each task's final step.

- [ ] **Step 2: Install**

Run: `npm install`
Expected: no `ERESOLVE`.

- [ ] **Step 3: Switch the PostCSS plugin to the v4 package**

Edit `packages/web/postcss.config.js` from:
```js
export default {
  plugins: { tailwindcss: {}, autoprefixer: {} },
};
```
to:
```js
export default {
  plugins: { "@tailwindcss/postcss": {}, autoprefixer: {} },

```

- [ ] **Step 4: Replace the @tailwind directives and load the legacy config**

Edit the top of `packages/web/src/styles.css` from:
```css

```
to:
```css
@import "tailwindcss";
@config "../tailwind.config.js";
```
(Leave the rest of `styles.css` unchanged. The `@config` directive makes Tailwind 4 read the existing `tailwind.config.js`, which keeps the `@journeyman/theme/tailwind-preset` preset, the `content` globs, and the `@tailwindcss/typography` plugin working without a rewrite.)

- [ ] **Step 5: Run the gate**

Expected: all exit 0. The critical signal here is `npm run build:web` compiling the CSS without "unknown utility" / "cannot resolve `@config`" errors.

- **Renamed/removed utilities:** v4 renames a set of v3 classes (e.g. `shadow-sm`→`shadow-xs`, `outline-none`→`outline-hidden`, removed `bg-opacity-*` in favor of `bg-black/50`).   ```bash
