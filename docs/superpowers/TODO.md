## Dynamic-provider spec — dry-run findings (resolve one by one)

From the end-to-end trace of [2026-06-01-dynamic-coding-provider-design.md](specs/2026-06-01-dynamic-coding-provider-design.md). Work through in order:

1. ✅ **RESOLVED (folded into Job 4 — Option B, unified).** [Job 4] No run-end hook for the local/in-process workspace. **Fix:** the **worker owns the workspace lifecycle for both local and docker** (one owner, one mental model). Worker provisions-if-missing on first step (local → `<base>/<runId>`; docker → create/connect container via daemon), records it, and a reaper cleans up at run end (docker via the recorded daemon connection; local via a worker-host sweep). api-server no longer owns workspaces (optional docker pre-warm only). Underlying reason: docker is remotely manageable, local is a folder on one machine — the worker is the one component that can do both.
2. ✅ **DOCUMENTED (Job 4 constraint).** [Job 4] Local workspace can't be shared across steps in a multi-worker deployment. A local folder on worker A isn't visible to worker B. **Resolution:** local = single-host / shared-FS only; **Docker is the multi-worker/distributed path.** No code change.
3. ✅ **RESOLVED (folded into Job 4).** [Job 4] Harness creates a redundant per-node workspace even for Docker runs ([worker-harness.ts:132](../../packages/orchestrator/src/workers/worker-harness.ts)). **Fix:** retire `DirectoryWorkspaceProvider`; harness uses the provisioned env's workspace (sandbox `/workspace` for docker, per-run dir for local). Also resolves the `DirectoryWorkspaceProvider` vs `LocalExecutionEnvironment` duplication.
4. ✅ **RESOLVED (folded into Job 3).** [Job 3] `ctx.materialize` wiring. **Fix:** `sandboxResolver` returns the execution environment (both `exec` + `materialize`); harness sets `ctx.exec` and `ctx.materialize`. Docker = wipe + `putArchive`; local = wipe + copy. Falls out of #1's unification.
5. ⏳ **FUTURE WORK (keep current behavior for now).** [minor] Skill-cache refresh race. Today every resolution `git fetch/reset`s the shared package dir ([resolver.ts:24](../../packages/skills/src/resolver.ts)); concurrent steps on the same package can race. **Decision: leave pull-every-time as-is for now.** Future: handle differently — e.g. per-package lock, pull-once-per-run with a pinned commit, or content-addressed (per-commit) paths for consistency + no races.
6. ✅ **RESOLVED (folded into spec §3f — make it loud).** [minor] MCP/skills resolution requires `userId` + `orgId`; runs without it silently resolved empty ([worker-harness.ts:203,232](../../packages/orchestrator/src/workers/worker-harness.ts)). **Fix:** if a step has skills/MCP configured but `userId`/`orgId` is missing, fail the step with a clear error (or loud warning) instead of silently dropping them.

## Worker-owned workspace (Option B) — dry-run scenarios (review one by one)

From the second end-to-end trace, after switching Job 4 to worker-owned provisioning:

A. ✅ **REVIEWED — folds into Job 4 / `ensureWorkspace`.** Provisioning ready-window race. **Resolution:** DB as referee — "insert-if-absent" elects exactly one builder; record carries a status `provisioning → active`. The builder provisions then flips to `active`; any other worker **waits/polls until `active`** (with a timeout that fails the step → ties to C). Postgres `LISTEN/NOTIFY` noted as an optional push-based upgrade over polling. Rejected: long-held locks (bad for minutes-long image pulls); a separate up-front provisioning step (re-adds the complexity we removed).
B. ✅ **REVIEWED — document now, per-branch = future.** Parallel steps share one workspace (fork/join) and can clobber each other if they edit the same files. Pre-existing (not caused by Option B). **Resolution:** document the constraint — "parallel branches that touch the workspace shouldn't write the same files." Per-branch subfolders / full per-branch workspaces deferred as a future enhancement (only if a real need arises; cost = repo sharing + join merge).
C. ✅ **REVIEWED — reuse A's flag; watchdog stays a DB-scan.** `"provisioning"` status + `ProvisioningReaper` move. **Resolution:** reuse the room record's `provisioning → active` flag (Scenario A). The **worker** sets it (`provisioning` on build start, `active` when ready), because it does the work. The **watchdog/`ProvisioningReaper` stays where it is** (api-server is fine — it just reads the DB and marks failed) but watches the **room-record flag** instead of the old up-front run status; a record stuck in `provisioning` past timeout → fail run/step + clean up. Same timeout serves A's wait-for-ready.
D. ✅ **REVIEWED — two-layer cleanup + document.** Orphaned local folder if its worker dies. **Resolution:** (1) normal — worker sweep removes finished-run folders; (2) backstop — age-based TTL sweep on worker (re)start reclaims orphans from crashes regardless of run status. Document that local cleanup is per-host (a dead host's folders wait until that host runs a worker again). Docker orphans are reaped centrally via the daemon connection — unaffected.
E. ✅ **REVIEWED — real bug; idempotent clone.** Retry reuses a dirty workspace. **Confirmed bug:** clone does a plain `git clone … repoDir` ([clone-repos.ts:76](../../packages/git-provider/src/providers/github/operations/clone-repos.ts)); if `repoDir` exists from a failed attempt, git errors ("already exists, not empty") → the **retry fails**. **Resolution:** make clone idempotent — remove `repoDir` if present, then clone fresh. Custom-AI is naturally re-runnable. Do **not** auto-wipe the whole workspace on retry (would discard other steps' completed work) — each writing step cleans its own output. Document that retries reuse the workspace.
F. ✅ **REVIEWED — fold into #6 fail-loud.** Provisioning needs user/org. `resolveWorker(pool, {orgId, userId}, workerId)` needs user/org to pick the worker/image; if missing, can't provision. **Resolution:** widen the #6 loud-failure check — if a step needs a workspace (or skills/MCP) but the run lacks `userId`/`orgId`, fail with a clear message ("can't resolve worker/skills/MCP: missing user/org context") instead of silently doing the wrong thing.

## Third dry-run — skills internals / local path (review one by one)

G. ✅ **REVIEWED — fixed in spec §3d/§3e.** Claude skill materialize target was wrong. **Resolution:** `materialize` is a **generic primitive**; **placement is provider-specific** (small per-provider step on the worker, like `createCodingProvider`). **Claude:** bundle the skill **package dir(s)**, materialize into `/workspace/.journeyman/skills/<package>`, rewrite each `localPath` to the materialized package root (plugin path). **OpenCode (deferred):** `.opencode/skills/` + `permission.skill`. No serialization-to-self, keeps live logs/cancel simple. Confirmed: local Claude needs **no** materialize (loads skills from the pantry path); `materialize`/`putArchive` is **container-only**.
I. ✅ **REVIEWED — demand-driven provisioning.** No-tools step still provisions (static `requiresWorkspace = true`, [custom-ai-step-handler.ts:32](../../packages/orchestrator/src/workers/steps/custom-ai-step-handler.ts)). **Resolution:** make provisioning **demand-driven per step** — the handler requests a workspace only when `toolsRequireWorkspace(tools)` is true (it actually touches files). A pure-LLM step needs no room → runs in-process even on a docker worker. Replaces the static handler flag with a runtime decision; fits the lazy-provisioning model.
J. ✅ **REVIEWED — leave as-is (minor future cleanup).** Double secret resolution: harness resolves → `ctx.env` ([worker-harness.ts:170](../../packages/orchestrator/src/workers/worker-harness.ts)); the custom-ai handler resolves again ([custom-ai-step-handler.ts:122](../../packages/orchestrator/src/workers/steps/custom-ai-step-handler.ts)). **Not pure waste** — the handler resolves a *superset* (provider slots + the custom step's own DB-declared slots the harness doesn't know). Correct, pre-existing, tiny cost. **Decision: leave as-is**; future cleanup = handler reuses `ctx.env` and resolves only the delta. Out of scope for this change.
