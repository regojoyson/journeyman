Building it in Journeyman

Each phase is built as an Agent (one self-contained AI runner) or a Workflow (runs several BMAD agents). Rule: a human gate is just a Jira transition outside the flow — so a phase is a Workflow only when it runs more than one BMAD agent. Everything else is an Agent.

Agent vs Workflow — when to use which

AGENT  one BMAD agent

One agent does the whole phase: it clones the Hub (+repos), adopts the BMAD persona, does the work, writes its output, and either advances the Jira status (clean) or stops & notifies (flagged). Has its own trigger + notifications.

trigger: status→ agent: persona + clone + work + advance

e.g. Implementation, Code Review, Testing, Deploy

WORKFLOW  several BMAD agents

Runs more than one BMAD agent — in parallel (fork/join) or in sequence. Built on the canvas from cloneRepos + several custom-ai steps. A human gate is not a reason (that's just an external Jira transition / Hub-MR merge).

cloneRepos→ custom-ai: agent 1→ custom-ai: agent 2→ open Hub MR (GitLab MCP)

only Discovery (analyst ‖ architect) and Grooming (pm → po → sm)

The prompt — one template, reused

Whether Agent or Workflow step, the persona is loaded the same way. Only agentFile, task, and the paths change.

Workspace layout (what the agent sees)

Everything is cloned into one workspace dir as sibling folders — the Hub is project-hub/ and bmad-core/ lives inside it:

The real, copy-paste prompts — 9 agents + 5 workflow nodes (12 personas) — live in PROMPTS.md — each with its tools, MCPs (Jira + GitLab), and exact project-hub/ + sibling-repo paths. All run with no output — they act via the MCPs. Paste them straight into the matching custom-ai step.

The ticket stays light but holds breadcrumbs so any agent/human jumps to context fast; the key is the unique identifier across Jira ↔ Hub ↔ GitLab.

The flow reads Hub Path / Epic / Repos from the ticket (Jira MCP) to fill the template vars; agents write MR urls back into MR Links.

2 · Cloning (the workspace)

One workspace dir, each repo a sibling folder: clone the Hub → project-hub/ (brings bmad-core/ + all context), plus the story's repos: (resolved via project-hub/repos/registry.yaml) → api/, web/, … Agents set this as their repo selection; workflows use the cloneRepos step. The Hub is cloned for every phase; code repos only for phases that touch code.

3 · Gates (human-in-the-loop)

Block gates = a human performs the next Jira transition (or merges the Hub PR) — that transition is itself the trigger for the next phase. On-flag = the agent's needsHumanReview stops it and notifies. No special pause node needed for single agents; the 3 workflows can use a pause node if they need a mid-flow approval.

4 · Notify (every phase)

Agents use their built-in notifications (on success/failure → Slack/Jira); workflows add sendMessage / commentOnIssue.

5 · Advancing the status

A clean Agent advances by transitioning the issue (give it a Jira MCP/connection); a Workflow uses the transitionIssue step. On-flag → no advance, human takes over.

6 · Secrets

Attach the Jira MCP and GitLab MCP to the agents (that's how they transition issues, comment, and open MRs). Store Jira / GitLab / Slack tokens in the secrets vault, bound to the agents/steps. Coding provider = Claude via runCustomPrompt.

7 · The two new components build once

(a) Hub↔Jira sync — create issues from story docs + write jiraKey back; echo Jira status into frontmatter; push Hub content to the issue.
(b) Zone-1 trigger — a GitLab webhook receiver that turns an epic Hub-MR-merge into a run (epics have no Jira issue).

Build order

1) Hub repo + bmad-core + workflow.yaml · 2) the 9 Agents (one persona each) + their Jira triggers · 3) the 2 Workflows (Discovery, Grooming) · 4) the Hub↔Jira sync · 5) the Zone-1 trigger · 6) dry-run one epic end to end.
